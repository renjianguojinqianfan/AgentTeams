# ADR-003-零侵入边界：默认策略 vs 可突破例外

## 状态
- **状态**: Accepted（修正 ADR-001/002 中对"零侵入"的绝对化表述）
- **日期**: 2026-08-09

## 背景
servevo 早期红线将"官方源码零侵入"视为**必须**（不改 `AgentTeams/` 下 servevo/ 以外的官方文件）。但经大赛信息核实（GOAI 官网 tracks 页 + 官方公告 + AgentTeams 仓库 LICENSE）：

- **大赛未禁止修改官方源码**：只要求以 AgentTeams 为"协同设计基点"，评审核验角色编排/任务拆解/上下文传递/状态追踪如何"映射到框架能力"，不关注是否改源码。
- **许可允许修改**：AgentTeams 为 **Apache-2.0**（宽松许可），允许修改与再分发，仅需保留版权声明；改动官方源码在许可上完全合法。
- **复赛代码包要求是"可执行"**：需含运行入口/依赖/配置/样例/运行证据——不是"纯净增量 diff"。

同时，纯零侵入有硬边界：部分能力（真正接 MinIO 宿主机、定制 Worker 审批流、copaw 深层扩展）需动官方扩展点，硬撑零侵入只能等价物替代或 presenter 兜底，反而牺牲"工程落地与运行验证（20%）"。

## 决策
**将"零侵入"从硬红线降级为"默认策略 + 可突破例外"**：

1. **默认零侵入**：servevo/ 内纯增量实现，保持 diff 干净、代码包可独立应用、答辩"可回滚"叙事成立。这是默认且优先。
2. **可突破例外**：当某能力必须动官方文件时，**允许改**，但优先走官方**已预留扩展面**（copaw `--package` / `spec.env` / CRD / 插件平台 / env 注入），仅在扩展面不足时才改官方核心源码。
3. **改动记录义务**：任何 servevo/ 外改动必须满足：收敛到最小、走扩展面优先、在踩坑手册记录、答辩主动声明"动了哪、为什么、如何回滚"。
4. **verify 闸门统一**：`servevo/verify.sh` 的"零侵入核对"改为"**核对 servevo/ 外改动是否被记录**"——未记录的 servevo/ 外改动视为违规，已记录的可通过。

## 证据
1. GOAI 官网 tracks 页：复赛代码包要求（可执行、含运行入口/依赖/配置/样例/运行证据），未要求纯净 diff
2. AgentTeams 仓库 LICENSE = Apache-2.0（宽松许可，允许修改分发）
3. 官方公告：AgentTeams 为"必选协同设计基点"，评审核验"映射到框架能力"而非源码封锁
4. P3.4 实测：MinIO 仅在容器内可达，host 无法直连 → 等价物替代（零侵入代价的实证）

## 后果
+ servevo/ 内增量保持默认纯净，代码包可独立应用（评审判定友好）
+ 撞墙能力可以走官方扩展面/改源码，不再硬撑等价物（提升"工程落地"得分）
+ 答辩可主动讲"哪里动了官方、为什么"，契合"缺失证据"准则（可信度加分）
- 需维护"servevo/ 外改动记录"清单（踩坑手册/ADR 溯源）
- verify 闸门的零侵入核对语义变更（从"禁止任何改动"改为"禁止未记录改动"），需同步 update verify.sh 与 AGENTS.md
