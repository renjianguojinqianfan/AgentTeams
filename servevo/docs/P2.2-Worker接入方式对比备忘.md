# P2.2 Worker 接入方式对比备忘（copaw 原生 vs 自定义镜像）

> 日期：2026-08-08 | 环境：Win11 + Docker Desktop 29.6.1（WSL2）+ AgentTeams v1.2.1 embedded
> 状态：✅ 路线 A 实证完成（代码级 + 容器实况双重确认）；路线 B 静态评估完成（未做动态 build）
> 结论：**copaw 原生路线（官方镜像 + YAML 人设 + skills 目录 + package 通道）胜出，全部需求已满足；自定义镜像降级为兜底方案**

---

## 0. 决策问题

servevo 需要 4 个角色（leader/cs/qc/coach）共用一套底座，两个候选接入方式：

| 路线 | 方案 | 人设注入 | 业务能力注入 |
|---|---|---|---|
| A | copaw runtime + skills/package 原生通道（官方 agentteams-copaw-worker 镜像） | Worker YAML 的 `identity/soul/agents` 字段 | `skills/` 目录 + `--package` zip |
| B | 自定义镜像（servevo/image/ Dockerfile，entrypoint 读 SOUL.md 定角色） | 同上（YAML→SOUL.md） | 镜像层预装依赖 |

---

## 1. 路线 A 实测证据链（agentteams-worker-alice 实况 + 源码）

### 1.1 关键事实：现有 alice 就是 copaw runtime

```
$ agt get workers
NAME   PHASE    MODEL        TEAM  RUNTIME
alice  Running  qwen3.7-max  -     copaw
```

镜像：`higress-registry.cn-hangzhou.cr.aliyuncs.com/agentteams/agentteams-copaw-worker:latest`

### 1.2 workspace 落地形态（MinIO `agents/alice/`）

```
agents/alice/
├── SOUL.md            # 44B：identity 字段生成 → "You are alice, an AI worker agent."
├── AGENTS.md          # 9.4K：内置 Worker 模板（agentteams-builtin-start/end 标记）+ agents 字段自定义段
├── openclaw.json      # agent 主配置（agents.defaults: maxConcurrent/memorySearch...）
├── .copaw/            # copaw 运行时状态（config.json=channels、copaw.log、skill_pool=内置技能池、providers.json）
├── .copaw.secret/     # 密钥（master_key、激活模型）
├── skills/            # AgentTeams 同步技能目录（communication/file-sharing/find-skills/mcporter/organization/task-management）
└── .agentteams-keep
```

### 1.3 容器内布局（copaw 与 openclaw 不同！）

```
HOME=/root/agentteams-fs/agents/alice          # 运行时工作区（.agentscope-runtime/logs/.mc.bin/.agents）
/root/.copaw-worker/alice/skills/              # ★ 技能落点（标准空间），~/.agents/skills 软链指向这里
/root/.copaw-worker/alice/workspaces/default/  # copaw 实际工作区（bridge.py 把 prompt+skills 灌入）
```

> ⚠️ 坑：copaw 的 skills 目录在 `/root/.copaw-worker/<name>/skills`，不是 `~/skills`；踩坑手册"五.4"修复流程对 openclaw 描述的逻辑需按此修正理解（copaw 靠 AgentConfigWatcher + 同步刷新）。

### 1.4 生命周期机制（源码级确认）

**创建**（controller 侧）：
1. `agt create worker --name X --identity "..." --soul-file SOUL.md --skills s1,s2 --package <uri>` 或 Worker YAML `agt apply -f`
2. `Deployer.WriteInlineConfigs`：identity/soul → SOUL.md；agents → AGENTS.md 自定义段（`deployer.go:266`）
3. `Deployer.DeployPackage`：解包 zip，`skills/` → MinIO `agents/<name>/skills/`（mc mirror），config/cron 同落位（`executor/package.go:175`）
4. `DeployWorkerConfig`：openclaw.json 等生成灌入 MinIO

**启动**（copaw 容器侧）：
5. entrypoint 拉取 MinIO → `/root/.copaw-worker/<name>/`（standard_dir）
6. `bridge.py bridge_standard_to_runtime`：SOUL.md/AGENTS.md（prompt 文件）→ `workspaces/default/`；controller 配置 → copaw 配置；skills 同步；mcporter 配置（`bridge.py:20`）
7. `worker.py _sync_skills`：`skills/<skill>/` 全目录镜像（SKILL.md + scripts/ + references/，.sh 补 +x）→ `workspaces/default/skills/`，覆盖内置、清理陈旧（`worker.py:509`）

**生效确认**（本次实测）：
- MinIO 上传 `agents/alice/skills/echo-test/SKILL.md`（106B）→ `docker restart agentteams-worker-alice` → 容器内 `/root/.copaw-worker/alice/skills/echo-test/` 出现 ✅
- copaw.log 更新、进程正常（`10:22:43 | Successfully preloaded agent: default`）

### 1.5 `--package` 通道（官方扩展面，路线 B 的替代者）

- `agt create worker --package` 支持 `nacos:// | http:// | oss:// | file://`
- controller 用 `NewPackageResolver(/tmp/import)` 解析解包（`package.go:33`）
- package 布局（`package.go:133`）：`skills/`（可选，自动 mc mirror 到 MinIO skills/）+ 顶层 config 文件 + cron 等
- **意义**：业务代码/技能包可以不重建镜像、不改官方源码，zip 即装即用；file:// 支持本机目录（Demo 双轨兜底通道之一）

## 2. 路线 B 静态评估（servevo/image/ 自定义镜像）

### 2.1 可复用资产
- 官方 `AgentTeams/worker/Dockerfile`（openclaw 版）与 `copaw/Dockerfile` 均为薄封装：基于 openclaw-base + 拷贝 entrypoint/共享库
- 自建镜像可 `FROM agentteams-copaw-worker`，覆盖 entrypoint 增加启动逻辑

### 2.2 增量的价值（真正需要的才自建）
| 需求 | 路线 A 能否覆盖 | 说明 |
|---|---|---|
| 四角色人设 | ✅ | YAML 的 identity/soul/agents 字段 → SOUL.md/AGENTS.md |
| 四类 Skill 包 | ✅ | skills/ 目录 + file:// 包，版本目录放 MinIO |
| 三图业务代码（rag/eval/adaptive 迁移） | ✅ | skills/scripts 或 package zip 注入；copaw 本身即 Python/AgentScope 栈，依赖与底座同构 |
| 特殊系统依赖（原生库/编译工具） | ❌ | 需自建镜像预装（当前无此需求） |

### 2.3 成本
- 维护面：镜像构建/推送/拉取、官方升级跟进（changelog 政策要求记变更）
- 同步机制需自行处理或依赖官方共享库（worker-file-sync.sh 可复用，但脱离官方容器编排后要自己接）
- 与"知识即 Skill、版本化发布"叙事重叠度低——技能演进应在 skills/ 目录而非镜像层

---

## 3. 结论与落地建议

1. **定夺：路线 A 主用**。servevo 全部需求（4 角色共用镜像、人设声明、四类 Skill、版本化）官方原生通道全覆盖，零侵入红线自动满足。
2. **servevo/README.md 目录规划微调**：`image/` 从"必建"降级为"兜底预案"（README 同步更新；规划 v3.2 的"共用同一镜像"架构决策不变——共用的是**官方 copaw worker 镜像**）。
3. **Worker YAML 模板**（P4 待建，字段已确认）：`identity`（一句话人设）→ SOUL.md；`soul`（详细人设 markdown，优先）→ SOUL.md；`agents`（工作协议）→ AGENTS.md 自定义段；`skills`（内置）+ `package`（业务 zip）。
4. **四类 Skill 落地路径**（P3/P4）：`servevo/skills/<name>/` 编写 → `file://` package 或直接 mc 上传 MinIO `agents/<name>/skills/` → 重启 worker 生效 → 版本化 = MinIO 版本目录 + label 寻址（与规划 §4.3 一致）。
5. **残留风险**：copaw 的 `workspaces/default/` 内 prompt 合并优先级、多角色同时挂同一 manager 的房间分诊、package 更新（isUpdate）对运行中 worker 的生效方式——留待 P4 team.yaml 验证。

## 5. 附：P2.4 知识包 file:// 通道验证（2026-08-08）

### 验证对象
`servevo/knowledge/product-knowledge/v1/`（星辰咖啡机知识，SKILL.md 契约 + references/ 三文档）→ zip（布局 `skills/product-knowledge/...`）→ `agt create worker --package file:///tmp/import/<zip>`。

### 实测结果 ✅
1. **file:// 解析**：controller 在容器内 `/tmp/import/` 解包（`executor/package.go ResolveAndExtract`，支持 file/http/oss/nacos/minio 路径）
2. **MinIO 落地**：`agents/cs-demo/skills/product-knowledge/{SKILL.md,references/*}` 4 文件（与官方 6 技能并列）
3. **容器落地**：`/root/.copaw-worker/cs-demo/skills/product-knowledge/`（重启/初始化后同步）
4. **copaw 启动**：2/2 agents，AgentConfigWatcher 运行中；工作区 `CoPaw_QA_Agent_0.1beta1/` 内 SOUL.md/AGENTS.md/PROFILE.md 灌入 ✓

### 重要发现（P3.1 需注意）
- **copaw 工作区 `skills/` 目录 = copaw 内置技能池**（skill_pool 回写，15 个：browser_cdp/docx/...）；**AgentTeams 注入的 skills 不进这个目录**
- ⚠️ 目录≠注册：注入技能实际注册进工作区 manifest `.copaw/workspaces/default/skill.json`（source=customized，7 技能全量含 product-knowledge）——见 §5.3 实验
- 结论（修正）：standard 区 skills/ 知识**已被 agent 消费**（见 2026-08-09 实验），消费机制=manifest 注册+agent 主动读 references，无需复制进内置池
- 知识包版本化：zip 名/版本目录（v1/）+ MinIO 版本 → 与规划 §4.3 一致

### §5.3 知识可见性实验（2026-08-09，R 方案实证 ✅）

**实验方法**：manager 账户经 Matrix API（createRoom + send/m.room.message）向 cs-demo 发问"PHONE 保修期"，观察 agent 行为与 log/session 证据。

**实测结果**：
1. **消息链路通**：DM → cs-demo → 回复（房间 `!DJHFD8…`，copaw 侧 session 落盘 `.copaw/workspaces/default/sessions/`）
2. **知识可见**：cs-demo 明确回答"查阅了星辰咖啡机产品知识库，未收录 PHONE- 产品"，并正确列出真实型号 K1/K2 —— 无幻觉否定 ✓
3. **注册证据**：`.copaw/workspaces/default/skill.json` 7 技能 source=customized（communication/file-sharing/find-skills/mcporter/organization/**product-knowledge**/task-management）
4. **scope 证据**：agent 能读到 references 内容（回答引产品型号）→ 标准区 references 可被工具读取

**结论**：R 方案（主动读 references）胜出，C 方案（复制进内置池）不需要。P3.1 检索实现 = 保留 references 文件布局 + copaw 可读通道（file_reader 等已有），仅需补齐 RAG 图的检索节点（keyword 优先，规避pgvector 红线）。

**遗留**：①MinIO 实际 7 文件（SKILL.md+6 refs：products/warranty-policy/faq/overview/pricing/refund-spec）较本地 `servevo/knowledge/.../v1/` 多 3 个（overview/pricing/refund-spec）→ 版本漂移，待对齐；②知识命中依赖 agent 主动检索念头，检索提示需在 SOUL/AGENTS 层显式声明（P3 落地项）

### 知识包布局（复现）
```bash
# 打包（zip 根下必须有 skills/ 前缀）
python -c "import zipfile,os; base=r'...\knowledge\product-knowledge\v1'; \
[z.write(os.path.join(r,f),'skills/product-knowledge/'+os.path.relpath(os.path.join(r,f),base).replace(chr(92),'/')) \
 for z in [zipfile.ZipFile(r'...\product-knowledge-v1.zip','w',zipfile.ZIP_DEFLATED)] for r,_,fs in os.walk(base) for f in fs]"
docker cp product-knowledge-v1.zip agentteams-controller:/tmp/import/
docker exec agentteams-controller agt create worker --name cs-demo --runtime copaw \
  --model qwen3.7-flash --soul "..." --package file:///tmp/import/product-knowledge-v1.zip
# 验证
docker exec agentteams-controller mc ls -r agentteams/agentteams-storage/agents/cs-demo/skills/product-knowledge/
```
